How the Agentic SDLC Pipeline works

A GitHub Copilot–driven pipeline that takes one Jira story (project EPMCDMETST) all the way from a requirements conversation to a merged pull request and a published Confluence summary — with a human approval at nearly every step, and without ever reading the target application's source code.

1 Conductor 7 Stage Agents 4 Doc-Sync Sub-agents 7 Skills 7 Guardrails (G1–G7) 2 Lifecycle Hooks App-agnostic via app-profile.yml

Inputs & Outputs, at a glance

What the pipeline needs before it can start, and exactly what exists once it finishes.

Takes in

  • A user story — from Jira (EPMCDMETST-<number>), a Confluence page, or a local Word document
  • .github/config/app-profile.yml — the one-time, human-filled description of the target app (stack, data model, run commands, repo, Confluence space)
  • Human answers to clarifying questions at each documentation step
  • Human approvals at every checkpoint (chat approvals, PR review, merge, publish)
  • Human-reported test pass/fail counts (the pipeline never fabricates test results)

Produces

  • docs/<STORY_ID>/ — one folder per story holding requirements.md, architecture.md, design-review.md, impl-plan.md, code-review.md, verification.md, trace-log.md, handoff.md
  • A feature branch with the docs bundle, implementation code, and generated tests committed
  • An open pull request with five required sections, merged by the human
  • A CHANGELOG.md entry for the story
  • A single Confluence summary page for the story
  • A test evidence log under the app's configured evidence path

End-to-end flow

The Conductor hands control from one agent to the next. Every arrow down is a stage boundary; every ✋ is a point where the pipeline stops and waits for a human.

The Conductor

agents/conductor.agent.md — the single entry point you select from the Copilot Chat agent picker to run the whole thing.

Master controller Claude Sonnet 4.5

Pipeline Conductor

.github/agents/conductor.agent.md

Drives the capstone's full lifecycle for one story, handing the baton to each stage agent in turn and holding at every human checkpoint. It is deliberately thin: it never talks to Jira, GitHub, or Confluence itself — it only routes between the agents that do, so each integration stays owned by exactly one agent.

Starts with

  • A story id (EPMCDMETST-<number>), or nothing to browse the backlog
  • Checks config/app-profile.yml is filled in before Intake runs

Delegates to, in order

  • Story Intake → Documentation Sync (4 sub-agents)
  • Build → Review → Verify → Release → Publish

On stage failure

  • Reports the stage and cause plainly
  • Offers retry, or skip (only Architecture, Design Review, Impl Planning are skippable)
  • Re-runs only the failed stage — never restarts the pipeline

If the chat session dies

  • Reads docs/<STORY_ID>/handoff.md in a fresh session
  • That file always names the next agent to pick and what to hand it

Stage agents

Seven picker-selectable agents, each owning exactly one part of the lifecycle. Every card below lists what triggers it, the skills and sub-agents it relies on, its checkpoint behaviour, and the guardrails/hooks it follows.

Entry point No checkpoint of its own

Story Intake

.github/agents/intake-agent.agent.md

Gets the pipeline a story to work on — from Jira, a Confluence page, or a Word document — and normalises all three to the same fields (title, description, acceptance criteria, estimate, status, owner).

Starts when

  • No story id given (browse mode)
  • A story id EPMCDMETST-<number> is given
  • A Confluence page or local .docx is pointed at

Uses (skills)

  • story-fetcher — browse / fetch, via Atlassian MCP
  • workspace-writer — trace-log entry only

Guardrails

  • G1 — Jira is read-only; this is the only agent allowed to reach it, and it never creates/updates/transitions/deletes an issue

Hooks

  • before-work: skipped — no file input (MCP / local doc)
  • after-work: logs once a story id is locked in, Checkpoint N/A

Documentation Sync

.github/agents/doc-sync-agent.agent.md

The heart of the "Automated Documentation Sync" use case. Runs four document-authoring sub-agents in strict sequence, each gated by its own chat approval, before anything is committed.

Starts when

  • Intake hands over a confirmed story id + fetched details

Calls (sub-agents, in order)

  • Requirements Author → requirements.md
  • Architecture Author → architecture.md
  • Design Critic → design-review.md
  • Work Planner → impl-plan.md

Guardrails

  • G2 — never commits or opens a PR; everything stays local until Build bundles it

Hooks

  • before-work: ensures the story's own docs/<STORY_ID>/ folder exists
  • after-work: collects all four sub-agents' rows and writes them to trace-log.md in one batched call

Came from Story Intake · Hands off to → Build Agent

Capstone Step 5 — Implementation No checkpoint

Build Agent

.github/agents/build-agent.agent.md

The first agent that writes to git. Cuts the feature branch, makes the first commit (the whole documentation bundle), then implements the approved plan task by task. Deliberately does not open a PR — that only happens later, at Release (capstone Step 8).

Starts when

  • Doc Sync hands over all four approved docs

Uses (skills)

  • workspace-writer — write code files
  • branch-committer — branch, stage, commit, push (GitHub MCP)

Guardrails

  • G5 secrets from env only · G4 stay inside data_model.entities
  • G7 build only what the plan covers · G2 feature branch only, never merges

Hooks

  • before-work: confirms all four docs exist
  • after-work: logs the branch + commits, Checkpoint N/A

Review Agent

.github/agents/review-agent.agent.md

Reviews the implementation as a peer reviewer would, before the PR exists — matching the capstone's "review before creating the PR" order. Findings are written to a file, not posted anywhere yet.

AreaWhat's checked
CorrectnessBehaves as requirements.md specifies
SecurityNo secrets in output; input validated
Error HandlingFailures, missing data, empty states handled
Test CoverageHappy path and not-found / missing-field edges
Code ClaritySelf-explanatory names, easy-to-follow logic
DRYDuplication worth refactoring
Dependency SafetyKnown-vulnerable package versions

Uses (skills)

  • workspace-writer — writes code-review.md

Guardrails

  • G6 findings only get posted (later, by Release) once the human says so
  • G7 stays in its lane — findings file only

Next → Verify Agent

Capstone Step 7 — Verify 2 checkpoints

Verify Agent

.github/agents/verify-agent.agent.md

Verification is two halves, per the capstone: the code (unit + integration tests against the running app) and the documents (a content-quality pass over the four synced docs). Also folds in standing the app up locally.

Uses (skills)

  • workspace-writer — writes verification.md
  • branch-committer — commits generated tests
  • evidence-logger — records human-reported pass/fail

Reads from app-profile.yml

  • local_run.* — install / build / start / url
  • quality.* — test tool, tests path, evidence path

Guardrails

  • G4 test results come only from the human, never fabricated
  • G2 tests committed to the branch; no push to base, no merge

Checkpoints

  • Confirm test scope before generating
  • Wait for the human's pass/fail report

Next → Release Agent

Capstone Step 8 — PR 2 checkpoints

Release Agent

.github/agents/release-agent.agent.md

The culminating step: opens the pull request (only now — after build, review, and verify), adds a changelog entry, and attaches the already-approved review findings to the PR. The human always performs the merge.

Required PR sections

  • Summary
  • Changes Made
  • Test Evidence
  • Known Limitations
  • Reviewer Checklist

Uses (skills)

  • branch-committer — commits CHANGELOG.md
  • pull-request-opener — opens the PR (GitHub MCP)
  • review-poster — posts the Review Agent's findings

Guardrails

  • G6 nothing posts before the human sees the exact content
  • G2 the merge is always a manual human action

Checkpoints

  • Human okays the PR body + CHANGELOG before anything posts
  • Human merges the PR and confirms

Publish Agent

.github/agents/publish-agent.agent.md

Rolls every artifact the pipeline produced into one Confluence summary page — the "sync" the use case is named for — so the work is discoverable outside the repo.

Page sections

  • Story Overview · Architecture & Design · Code Changes
  • Review Outcome · Verification Results · PR Reference

Uses (skills)

  • page-publisher — create/update the page (Atlassian MCP)
  • workspace-writer — final trace-log row

Guardrails

  • G3 only this one page, only in the configured space, never deleted
  • G4 missing info is marked [pending], never invented

Next — none, the pipeline is complete 🎉

Documentation Sync sub-agents

Four narrow, single-purpose authors invoked only by the Documentation Sync agent — never selectable directly from the picker. Each owns exactly one file and refuses to touch any other author's output.

1 · Requirements Author requirements-author.subagent.md

Turns the intake story into requirements.md by asking five clarifying questions in a single message (constraints, dependencies, definition of done, NFRs, exclusions) and compiling the answers against templates/requirements.template.md.

uses: workspace-writer → writes requirements.md → hands back to Doc Sync

2 · Architecture Author architecture-author.subagent.md

Designs components, technology picks, and data flow for the approved requirements, staying on the stack declared in app-profile.yml and never naming an entity outside data_model.entities.

uses: workspace-writer → writes architecture.md → hands back to Doc Sync

3 · Design Critic design-critic.subagent.md

Acts as a senior reviewer of the architecture before any code exists — scoring it through five lenses (correctness, security, scalability, scope, error handling) and giving a verdict of APPROVED or NEEDS CHANGES.

uses: workspace-writer → writes design-review.md → hands back to Doc Sync

4 · Work Planner work-planner.subagent.md

Breaks the approved requirements + reviewed architecture into a dependency-ordered task list with stable ids (T1, T2 …), effort ratings, and explicit blocked-task calls.

uses: workspace-writer → writes impl-plan.md → hands back to Doc Sync

Skills

Single-purpose, reusable actions. Agents never call an external system directly — they always go through one of these seven skills, each scoped to exactly one job.

story-fetcher

Used by: Story Intake

Browses/fetches a Jira story, or reads one from Confluence/Word. Read-only — via the Atlassian MCP server.

workspace-writer

Used by: almost every agent

Writes/updates a file in the repo safely. Local filesystem only; refuses .env, path escapes, empty content.

branch-committer

Used by: Build, Verify, Publish

Cuts the feature branch, stages named files, commits, pushes — via the GitHub MCP server. Never pushes to base, never merges.

pull-request-opener

Used by: Release

Opens the PR with the five required sections via the GitHub MCP server. Won't duplicate an existing PR.

review-poster

Used by: Release

Posts the already-approved review findings as PR comments, tagged Issue/Suggestion. Never posts unconfirmed content.

page-publisher

Used by: Publish

Creates or updates the one Confluence summary page for the story, via the Atlassian MCP server.

evidence-logger

Used by: Verify

Records human-reported pass/fail counts into a dated evidence log. Never runs or fabricates test results itself.

Guardrails (G1–G7)

One shared, numbered rulebook (rules/guardrails.md) that every agent and sub-agent points to instead of restating. Change a rule once, it changes everywhere.

G1

Jira stays read-only

Only Story Intake reaches Jira, and only to browse/fetch — never create, update, transition, comment, or delete.

G2

GitHub writes go through named skills only

Commits via branch-committer, PRs via pull-request-opener, comments via review-poster. No agent ever merges — that's always a human action.

G3

Confluence: one page, one space

Publish may only create/update the single summary page in the configured space — never delete, never stray elsewhere.

G4

Everything traces to a real source

Every fact comes from the story, app-profile.yml, a file actually read, or a human answer. Gaps are marked [pending], never invented. The data model is closed to data_model.entities.

G5

Secrets stay out

No credentials in code or docs — environment or MCP server only. .env is never read, written, or committed.

G6

Checkpoints are real stops

A skippable stage still needs explicit human consent, and the skip is logged. Nothing external (PR, comment, Confluence page) posts before the human has seen the exact content.

G7

Stay in your lane

Each stage edits only the files it owns. A rejection routes back to the owning stage with a targeted patch — never a full regeneration, never a pipeline restart.

Lifecycle hooks

Two documentation-enforced hooks (hooks/lifecycle-hooks.md) every agent follows as explicit steps — there is no background runner executing these.

before-work

Runs before a stage does anything else: re-reads its own Inputs/Trigger, confirms app-profile.yml has the fields it needs, and checks every named input file exists on disk. If something required is missing, it halts and asks the human whether to run the missing stage first or abort — it never guesses forward.

after-work

Fires once per top-level agent run (not per internal step). It appends one row per internal step to docs/<STORY_ID>/trace-log.md in a single batched write, then overwrites docs/<STORY_ID>/handoff.md with a snapshot of the last finished stage, everything produced so far, and exactly which agent to pick next — the resume point if a chat session ever dies mid-pipeline.

Configuration files

What makes this pipeline work on any application, not just one.

config/app-profile.yml

The single human-maintained description of the target app: name, tech stack, data_model.entities (the closed list of things that exist), local run commands, GitHub repo, Jira project, Confluence space, and test tooling. Every agent reads this instead of inspecting source code — if a fact isn't here and isn't in the story, the agent asks rather than guesses.

config/pipeline-settings.md

Shared, non-secret knobs: branch/commit naming, the four synced-doc filenames and their authors, required PR sections, the seven-area review checklist, the Confluence page section order, and which stages can never be skipped (Intake, Requirements, Build, Verify).
